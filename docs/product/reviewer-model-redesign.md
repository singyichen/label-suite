## 1. 教授的三段要求

1. 審核員與標記員看到**相同的資料呈現**，同意 → 直接下一筆、不同意 → 當場改標籤（明確否決「只有通過／退回按鈕」的設計）
2. 標記員與審核員**一致即完成**；不一致時把不一致項**過濾聯集**成爭議資料，**指派第三人投票**；審核指派可一位或多位
3. 每筆資料的**審核歷程**（由哪幾個人標記與審核過），以及審核員的**登入時間 / 停留時長 / 實際審核筆數**

使用者補充兩點：不分 `dry_run` / `official_run` 都要滿足；清單要**逐標記員拆分**——同一筆原始資料，每個人的標記結果各自成為一列。

## 2. 已定案的五個決策

| # | 主題 | 決策 | 說明 |
|---|------|------|------|
| ① | 審核模型 | **統一逐標記員審核** | 廢除 `dry_run` / `official_run` 的審核分流，審核單位一律是「樣本 × 標記員」 |
| ② | gold 來源 | **dry_run 不產 gold** | 試標的產出是 IAA 與每位標記員的被修改率；gold 只在正式標記產生 |
| ③ | 仲裁粒度 | **逐項 A／B 二選一** | 只把不一致的標籤 / span / token 拉出來投票，兩人都同意的部分自動保留 |
| ④ | 多審核員定案 | **審核員間多數決** | N 位審核員逐項取多數決；平手或全數分歧才進爭議池 |
| ⑤ | 審核員份數 | **每筆需幾位，任務可設** | 「一式三份」只是例子。`min_reviewers` 是任意正整數，1 就是單一終審員 |

補充兩項定案（2026-08-14 追加）：

- **`task-new` Step 3 完全不加審核設定**。建立任務時還沒有成員，指派方式與仲裁者都無從選；`最少標記者數` 本來也只在 task-detail。連「每筆幾位審核員」這個純數字也不加——`min_reviewers` 建立時取預設值 1，之後在任務概覽調整。**連帶效果：spec 013 落在本次範圍外。**
- **爭議池不獨立頁籤**。審核員在標記清單用「爭議中」篩選處理；專案負責人在成員管理的「審核指派」區塊看到計數與分派鈕。爭議項本質是審核單位的一個狀態，為了一個計數多開一個頁籤不划算。

## 3. 當時現況與教授需求的落差（歷史盤點）

實機操作 prototype 四個頁面、走過兩種 run_type 與 8 種輸出類型後的盤點。**有兩項現況其實已經滿足需求，不需重做。**

| 教授需求 | 現況 | 判定 |
|----------|------|------|
| 審核員看到與標記員相同的資料呈現，可直接改標籤 | 修正控制項直接複用標記員元件，非另建專屬介面 | ✅ 已滿足 |
| 審核員登入時間、系統停留時長 | 工時紀錄已有 `login_at` / `logout_at` / `online_duration` / `duration` | ✅ 已滿足 |
| 同意 → 直接下一筆 | 介面宣傳 `A` / `R` / `Shift+A` 等快捷鍵，程式完全沒實作，實測按鍵無反應 | ⚠️ 效率缺口 |
| 審核了多少筆 | 只有單一 `completed_count`，標記筆數與審核筆數沒分開 | ⚠️ 部分落差 |
| 每筆資料由哪些人標記與審核過 | 標記端追得到人；審核端追不到——歷程字面是 `single_label · current: approve` | 🔴 地基缺陷 |
| 同一筆原始資料，每位標記員的結果各自成為審核單位 | 清單一列 = 一筆原始資料。dry_run 展開才見 3 人；official_run 直接砍成 1 人 | 🔴 核心改版 |
| 標記員與審核員一致即完成 | 沒有任何比對兩者是否一致的邏輯 | 🆕 新功能 |
| 不一致 → 過濾聯集 → 指派第三人投票 | 全 prototype 零實作。現行「分歧」是當下審核員自己拍板，不是指派第三人 | 🆕 新功能 |
| 彈性指派一位或多位審核員 | 有 `minAnnotators`（值 3），完全沒有審核員份數的對應欄位 | 🆕 新功能 |
| 不分試標或正式標記，兩者都要滿足 | 硬分流：`REVIEW_MODEL_BY_RUN_TYPE` 把 dry_run 綁共識仲裁、official_run 綁單人審核 | 🔴 要拆除 |

### 最該先修的不是介面，是身分

`annotation-workspace.data.js` 的 `submissionBucketKey(taskId, role, runType)` **不包含審核員身分**，任何審核員的提交都寫進同一個桶；official_run 的標記員身分則一律記成字串 `current`。

這代表「一式三份給三位審核員」和「每筆由誰審核過」在現有資料模型上**不是難做，是做不出來**。所有 UI 改版都必須排在這塊地基之後。

## 4. 當時目標流程（現行行為已由 015 取代）

同一套流程套用在試標與正式標記，不再依 `run_type` 分岔。唯一差別是 dry_run 一筆樣本有多個審核單位、且不產 gold。

```
審核單位   樣本 × 標記員
           清單一列 = 一個標記結果。一筆原始資料被 3 人標過，就出現 3 列，各自獨立審核
    ↓
審核       審核員看到與標記員完全相同的作答面板
           面板以該標記員的答案預先填入，可直接編輯（現行程式已做對，沿用即可）
    ↓
分岔       同意   → 直接下一筆：兩人一致，該審核單位定案。正式標記時即成為 gold
           不同意 → 當場改標籤：系統逐項比對兩人差異，只把不一致項拆成爭議項
    ↓
爭議池     不一致項自動聯集，可篩選、可指派。兩人都同意的部分不進池
    ↓
仲裁       第三人逐項在 A／B 之間投票
           沿用既有合併鍵：實體 start+end+type、關係 subj+obj+type、序列標記逐 token
```

### 審核員份數是任務設定值，不是固定 3

教授說的「一式三份」是例子，不是上限。任務設定要有一個 `min_reviewers` 欄位，由專案負責人自行決定一筆資料需要幾位審核員——設 1 就是單一終審員，設 3 就是三人並行，設 5 也成立。與既有的 `min_annotators` 同一層級、同一種輸入。

收斂規則不隨 N 改變：N 位審核員各自獨立審核後逐項取多數決（3 人中 2 位同意 → 採「同意」，不需第四人）。`N = 1` 時沒有多數決，標記員與審核員不一致就直接進爭議池；N 為偶數時平手同樣進爭議池。

## 5. 當時畫面提案（歷史）

### 5.1 標記清單

**現況**：一列 = 一筆原始資料

```
▼ emo-001  待處理  收到確診通知的…  sad×3 · fear×3  [編輯]
   ├ kioleemg12    sad, fear, surprise
   ├ 113450022     sad, fear, surprise
   └ tony0950127   sad, fear

▶ emo-002  待處理  治療結束後回診…  happy×3        [編輯]
```

展開明細唯讀，無任何決策控件；official_run 直接 `slice(0, 1)` 砍成一位標記員。

**目標**：一列 = 一個標記結果

```
emo-001 · kioleemg12    sad, fear, surprise  [審核]
emo-001 · 113450022     sad, fear, surprise  [審核]
emo-001 · tony0950127   sad, fear            [審核]
emo-002 · kioleemg12    happy, surprise      [審核]
```

- 篩選器新增：待審 / 已同意 / 已修改 / 爭議中
- 「標記分布統計」欄降級為唯讀輔助資訊
- dry_run 與 official_run 走同一套版面

### 5.2 審核作業頁

**現況**：兩套介面，依 `run_type` 分岔

```
dry_run ─ 共識仲裁卡                official_run ─ 單人審核卡
  統計盒 + 共識徽章「分歧 · 2/3 一致」   只有修正面板 + ✕ / ✓
  三位標記員逐人列（偏離標色）           標記員身分顯示為 current
  [套用多數決至全部分歧項]
  直接修正面板
```

**目標**：單一介面，兩種 run_type 共用

```
emo-001 · 標記員 kioleemg12       1 / 18

  （與標記員完全相同的作答面板，
    以該標記員的答案預先填入、可編輯）

  參考：本筆其他標記員的分布  sad×3 · fear×3
        ↑ 唯讀，不是決策入口

  [ 不同意 · 改標 ]   [ 同意 → 下一筆 ]
                       快捷鍵 A（待實作）
```

## 6. 當時設定與後台提案（現行行為已由 014 取代）

現有設定介面**完全沒有審核相關欄位**——任務只設得了「最少標記者數」，設不了「每筆要幾位審核員」。五個落點的盤點：

| 畫面 | 現況 | 要加什麼 |
|------|------|----------|
| task-detail › 任務概覽 | 「抽樣設定」區塊內有 最少標記者數（值 3）、抽樣筆數、資料隔離 | **新區塊** 與抽樣設定並列的「審核設定」 |
| task-detail › 成員管理 | 加入成員（角色只有標記員／審核員）＋成員清單 7 欄 | **新區塊** 審核指派；成員清單加「審核負荷」欄 |
| task-detail › 標記結果 | 表格 7 欄，展開列顯示標記分布統計；篩選只有標記員 | **改展開列** 改為審核歷程；篩選加審核員與審核狀態 |
| task-detail › 工時紀錄 | 登入／登出、上線時長、工作時長都已具備；筆數只有單一「完成筆數」 | **拆欄** 完成筆數拆成標記／審核／仲裁 |
| task-new › Step 3 啟動設定 | 只有每回合抽樣筆數＋資料隔離 | **不動**（已定案：審核設定一律在 task-detail） |

### 6.1 任務概覽 — 新增「審核設定」區塊

```
審核設定                        [編輯]

每筆資料審核員數  3        ← 對應上面的「最少標記者數」
審核指派方式      自動平均分配
一致即定案        啟用
第三人仲裁        啟用 · 仲裁者 2 人

──────── 編輯態 ────────
每筆資料審核員數 [ 3 ]
  任意正整數。1 = 單一終審員
  N ≥ 2 = 一式 N 份並行審核

審核指派方式
  ● 自動平均分配   ○ 手動指派
  自動＝系統輪派，每筆湊滿 N 位
  手動＝到成員管理逐一分派

☑ 標記員與審核員一致即定案
☑ 不一致時建立爭議項交第三人仲裁
   仲裁者 [ 選擇審核員 ▾ ]
   未指定＝任一未參與該筆的審核員可認領
```

**為什麼放這裡、不新開頁籤**：`最少標記者數` 已經在抽樣設定裡，「一筆要幾人標記」和「一筆要幾人審核」是同一類決定，相鄰擺放才對得起來。四個欄位獨佔一個頁籤不划算。

### 6.2 成員管理 — 新增「審核指派」區塊

```
目前成員清單（既有表格加一欄）
  姓名 | Email | 任務角色 | 審核負荷 | 狀態 | 加入時間 | 最後活動 | 操作
                          └ 標記員列顯示 —
                            審核員列顯示「40 筆 · 12 待審」

審核指派                        未指派 18 筆   [自動補齊]
  ← 指派方式為「自動平均分配」時此區塊唯讀，只呈現結果

  審核員            已指派   待審   已完成
  王小明             40      12     28    [指派…]
  李大華             40      31      9    [指派…]
  陳美玲  仲裁       18       5     13    [指派…]

  爭議池  7 項待仲裁                    [分派給仲裁者]
```

教授說的「彈性指派」拆成兩層：**要幾份**是任務設定（6.1），**由誰審**是成員指派（6.2）。這也符合現行 spec 013 FR-004a——建立任務時不做成員指派，因為那時還沒有成員。

### 6.3 標記結果 — 展開列改為審核歷程

```
篩選：標記階段 · 提交狀態 · 標記員 · 審核員 · 審核狀態   ← 後兩者為新增

▼ sent-001  已完成  08-12 14:03  正式

  標記員 kioleemg12  sad, fear   13:41 提交
    └ 審核員 王小明   同意        14:01
  標記員 113450022   sad         13:52 提交
    └ 審核員 李大華   修改→sad, fear  14:03
    └ 仲裁 陳美玲     採 B        14:20
```

直接對應教授的「必須能清楚看到每筆資料的審核歷史」。資料本來就要為 P1 記錄下來，這裡只是把它顯示出來。

### 6.4 工時紀錄 — 完成筆數拆成三欄

```
日期 | 成員 | 角色 | 登入／登出 | 上線時長
     | 工作時長 | 標記 | 審核 | 仲裁 | 平均速度 | 標記階段
                 └ 角色不適用者顯示 —

摘要：總工時 · 總標記筆數 · 總審核筆數 · 加權平均速度
```

登入時間與停留時長本來就有，教授三項要求裡缺的只有「實際審核了多少筆」，就是這一欄。

## 7. 當時資料模型提案（歷史）

| 實體 | 動作 | 內容 |

| `review_assignment_mode` | 新增 | 任務設定：`auto`（系統輪派，每筆湊滿 `min_reviewers` 位）或 `manual`（在成員管理逐一分派） |

| `TaskMember` | 修改 | 審核員成員補審核負荷衍生值（已指派／待審／已完成）與可仲裁旗標。**不新增任務角色**——仲裁者是審核員身上的旗標 |
| `WorkLogEntry` | 修改 | `completed_count` 拆成 標記筆數 / 審核筆數 / 仲裁筆數；新增每筆平均耗時 |
| `REVIEW_MODEL_BY_RUN_TYPE` | 廢止 | 審核模型不再依 `run_type` 分流 |
| `GoldRecord` | 縮限 | 只在 official_run 產生。dry_run 改以「每位標記員的被修改率」衡量品質 |
| `ADJUDICATION_STATUS` | 廢止 | 五態狀態機由 `ReviewUnit` 狀態 + `DisputeItem` 狀態取代 |
| `CONSENSUS_MERGE_KEYS` | 沿用 | 逐項比對一致性的規則不變，改用在「標記員 vs 審核員」而非「標記員彼此」 |

## 8. 歷史交付拆分（P1～P5）

動到 spec 015 與 014 兩份（013 因 task-new 不動而落在範圍外），遠超單一 PR 的 5 檔案 / 300 行上限。依相依順序拆分，每個 PR 各自可獨立驗收。

## 9. 當時連帶問題（現況回查 014／015／017 與 decision log）

- **下游 spec 017 會被影響**。「標記員品質排名」目前定義為「與共識／gold 的一致率排名」。dry_run 不產 gold 後，這個基準要改成「被審核員修改的比例」。
- **審核工作量會乘上標記員數**。dry_run 從「N 筆」變成「N × 標記員數」個審核單位。緩解靠「同意 → 直接下一筆」的快速通道與快捷鍵，這正是教授要求的效率設計。
- **anchoring bias 必須在論文誠實揭露**。審核員是看過標記員答案後才判斷，這個「一致」不是嚴格的獨立雙標一致率，不能拿來佐證資料品質。這是論文的揭露問題，不是系統問題。
- **共用常數治理已經先壞了**。`specs/_shared/constants.md` 聲稱 013、014 引用共用常數，但全 repo 實際寫出參照的只有 `specs/annotation/015-annotation-workspace/spec.md` 一份，另兩份都是內嵌重複定義。這次 015 與 014 都要改常數，不先上收會各自漂移。
- **Constitution XIII 站在教授這邊**。憲章早已要求「審核／仲裁流程必須在 task config 宣告」，現行 spec 用 `run_type` 硬綁反而違憲——這是對口試委員很強的論證。

## 11. 建議但不在本次範圍

研究顧問提出、但教授沒有要求的加值項。列在這裡供決定要不要納入，**預設不做**。

**抽樣盲審模式** — 每輪抽 10–15% 樣本，讓審核員在看不到標記員答案的情況下先自己標一次再比對，用這組數字校正「看得到答案的複核一致率」有沒有被高估。

對 Demo Paper 是加分項——現有工具都不區分這兩種模式。但它增加審核工時，也與「同意直接下一筆」的效率訴求相衝突。
