# Permission Matrix as Authorization Authority — Design

## Goal and scope

Resolve issue #1160 decisions D-9 through D-13 at the planning-contract level. Keep the editable role-permission matrix and its single-row version table as candidate entities, define exactly how a stored cell participates in authorization, and align the canonical role and task contracts before revising the physical dictionary and NoteCraft projection. This slice changes specifications, an authorization ADR, and candidate documentation only. It does not create ORM models, migrations, API endpoints, backend guards, frontend capability hooks, or deployed tables. Those require a separate implementation change with security Red tests.

## Evidence and authority boundary

Admin-007 says saved configuration becomes the later authorization baseline, defines a backend `permission_key` allowlist, a 39-cell V1 matrix, a version/ETag conflict check, multiple task roles, and an active task role for annotation workspace. Its `allowed` field is boolean, while the `reviewer` row describes `task.detail.view` as read-only without a separate edit key. ADR-021 currently illustrates `require_role` based on the fresh `users.role`; admin-006 and admin-007 require the admin screens to remain `super_admin`-only. Task-new-013 uses fixed system roles for creation; task-list-010 and task-detail-014 use fixed role checks for list/detail/actions. Task-detail-014 FR-005d excludes a person already in the task from another invitation, even though admin-007 permits that person to have several task roles. Foundation F-04 already requires server-side resource membership checks and API-provided capabilities; F-15 permits short-lived permission caching, but the constitution requires immediate revocation after role removal. Accepted ADR-032 reserves `role_permissions.changed` while leaving the singleton matrix target ID unresolved.

The authorization ADR must define the combination rule and trust boundary. Admin-007 owns the key registry, V1 rows, editable-cell invariants, save and audit behavior. Each consuming feature owns the mapping from its operations to a permission key and its additional resource conditions. A permission cell cannot grant a role or membership that the caller lacks, and no role may bypass a denied or absent applicable cell merely because a prototype shows an action.

## Decisions

1. **Server evaluation order.** Authenticate the current user and active token family; read current `users.role` and `is_active`; obtain the relevant active task memberships from the authoritative task store when a task scope exists; require the operation's allowlisted key and an `allowed=true` cell at the matching `role_type`/`role_key`; finally enforce task ownership, task state, assignment, reviewer roster, data isolation, and other operation-specific constraints. A missing/unknown key, missing row, wrong role layer, inactive membership, absent task, or failed resource condition denies. The role matrix is a necessary authorization input, never a replacement for membership or resource checks. Protected API routes enforce this order on the server, with `404` where revealing resource existence would leak data.
2. **Admin hard boundary.** Reading, editing, and auditing the matrix, and entering the two admin pages, remain limited to an active `super_admin` from the current database row; the matching `admin.*` matrix cell is an additional necessary check. The `user` role can never gain admin access by changing a cell. All `super_admin × admin.*` cells are fixed true and all `user × admin.*` cells fixed false. ADR-021's `require_role(super_admin)` remains useful for this non-configurable boundary, but ordinary feature guards also evaluate the matrix through a permission dependency. JWT `role` is display-only and task roles never come from JWT or global client state.
3. **Task role composition.** One user may hold several roles in one task. A task membership is identified by `(task_id, user_id, task_role)`; a second row with the same triple is forbidden, while a different task role is permitted. Task-detail-014's candidate search excludes a person only for a role they already hold, and status/removal applies to the selected membership rather than silently removing their other role. Non-workspace task-page access may use the union of allowed keys from active memberships in that task, subject to the page's specific resource constraints. Annotation workspace requires an explicitly selected active task role; annotate/review writes check only that selected role and its matching active membership, not the union. Changing a query parameter cannot impersonate a role or reviewer identity.
4. **Boolean view/edit split.** Keep `allowed boolean`. Add `task.detail.edit` as a separate task-level key. V1 task-role defaults are `project_leader=true`, `reviewer=false`, `annotator=false` for edit; existing `task.detail.view` remains `project_leader=true`, `reviewer=true`, `annotator=false`. A reviewer therefore has view without edit. The new key applies to all three task roles, so the seed grows from 9 platform keys × 2 system roles plus 7 task keys × 3 task roles = 39 rows to 9 × 2 + 8 × 3 = **42 rows**. The edit key does not override narrower conditions or distinct keys such as `task.members.manage` and `dataset.export`; operations require their explicitly mapped key and resource checks.
5. **Fixed cells, new keys, and fail-closed release.** The V1 matrix is an approved seed, not a rule that later keys inherit its grants. For each later permission key, the default for all *configurable* applicable cells is false; absent rows also deny. A key is not part of the active allowlist or callable authorization contract until a reviewed change defines its layer, operation mapping, complete rows, and security tests. Fixed cells are a narrow exception to the false seed: `super_admin × admin.*` stays true, `user × admin.*` stays false, and both system roles' `dashboard.view` stays true. A later `admin.*` key cannot be activated with all-false rows because that violates the existing `super_admin` invariant; its reviewed activation seeds the fixed super-admin true and user false values atomically with the approved allowlist change, while any other configurable applicable cells begin false. `dashboard.view` is an existing V1 fixed key, so the future-key default does not re-seed it; removing/reintroducing it cannot bypass its fixed-true rule. Until an activation is complete, an unknown or missing key denies. This preserves D-12's default-deny intent without creating an impossible state under D-13 or FR-008a.
6. **Applicable rows and protected writes.** Persist only the role/key pairs defined for that layer. The `⛔（需 task role）` system-role cells are inapplicable and have no row; `false` is reserved for an applicable but denied cell. Reject extra, missing, duplicate, or cross-layer cells on save. A matrix save takes the expected version; an atomic compare-and-swap advances the singleton version only when a real cell changes. The changed cells, version transition, and ADR-032 `role_permissions.changed` event commit in the same transaction. Derive the audit diff from server-observed rows; never trust a client-provided diff. The stable audit target is `target_type='role_permission_matrix'`, `target_id='1'`, matching the version singleton. Empty saves do not advance version or emit an event.
7. **Freshness and capability transport.** The first runtime implementation reads the current matrix for each relevant authorization decision, including after role/membership or matrix changes; do not use a TTL cache as proof of immediate revocation. A later cache requires a separately verified invalidation protocol covering role, membership, and matrix writes on both SQLite Lite and PostgreSQL. Frontend menus and buttons consume server-returned task-scoped capabilities for display, and every command is independently rechecked on the server. Capability responses must omit restricted answer data and use private/no-store caching. The design must distinguish an unauthorized request from a hidden resource without disclosing task existence.

## Candidate physical projection and traceability

`admin_role_permission` remains one row per applicable `(role_type, role_key, permission_key)` with that triple as its non-null composite PK, `allowed boolean NOT NULL`, and change time. `admin_role_permission_version` remains the one-row `id=1` version guard. Both cease to be labelled conditional on whether D-9 keeps editable authorization, but both remain **candidate, undeployed schema**. No new table is required for the key registry: the backend allowlist is the source, with complete approved seed rows and a fail-closed read. Keep NoteCraft at nine candidate tables, 63 columns, and six confirmed candidate FKs until dataset/task entities have a typed dictionary. The row-count change is seed policy, not an ER field-count change. Only confirmed physical FKs are drawn; neither a role key nor a task membership FK is invented in this account/admin view.

Canonical write-back must cover the new authorization ADR and admin-007 V1 keys, matrix, FR/SC, dependencies, and changelog. ADR-021 must distinguish its fresh-role hard gate from permission evaluation. Admin-006 keeps its super-admin boundary while adding the matching matrix condition. Task-new-013 `task.create`, task-list-010 list/detail/delete guards, and task-detail-014 view/edit/member/export conditions need explicit operation-to-key and resource mapping; task-detail-014 also owns the D-11 candidate/membership change. Annotation-015 owns active-role write isolation and cannot infer identity from route parameters. Foundation F-04 and F-15 already provide the API/resource and cache baseline; inspect whether a new SC is needed, but do not duplicate feature-specific key lists there. Dashboard-012 should be reviewed against the fixed `dashboard.view` invariant and task-membership visibility; its existing single primary-view priority does not collapse multiple stored memberships.

The V1 allowlist has no `task.delete` key even though task-list-010 permits deletion by a project leader or super administrator. It also has no general key for every task lifecycle command. The D-9 design must not imply those operations are authorized by an unrelated key or silently bypass the matrix. The consuming-spec write-back records an explicit action-coverage gap: before runtime converts each such operation, a separately reviewed key is added under the D-12 activation rule with matching hard role/resource conditions and revised seed count. A V1 matrix with 42 rows describes the currently enumerated keys; it is not a claim that all future API actions are mapped already.

## Verification and follow-up

Planning checks must confirm: 42 V1 applicable seed cells, separate `view`/`edit` keys with reviewer read-only, exact fixed-cell values, no stored `⛔` cross-layer cells, missing/unknown permission denial, stable audit target `1`, and the triple membership identity in canonical text. The OpenSpec change must pass schema validation and Project SDD lint; after archive, canonical FR/SC IDs and wording must be located in derived views. The account/admin dictionary and NoteCraft JSON must pass source-to-projection and plugin-schema checks; the actual Wiki and Diagram should show both matrix candidate tables and accurate draft/undeployed labels.

Runtime work is separate. Before any API or migration implementation, write failing security tests for current-role and membership revocation, matrix change visibility, absent/unknown cells, cross-task access, reviewer view-versus-edit, active-role workspace writes, protected admin endpoints, unauthorized/hidden resource responses, and answer isolation. Migration tests must cover the composite PK, allowed boolean, fixed-cell CHECKs, the 42-row seed, version compare-and-swap, audit atomicity, and SQLite/PostgreSQL behavior. The exact task table/PK and task-membership FK stay in the later task/dataset inventory slice; the logical triple is decided here without pretending its physical task FK is settled.
