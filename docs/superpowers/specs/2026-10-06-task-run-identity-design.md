# Issue #1160 — Task/run physical identity and lineage design draft

**Status:** Review draft with a selected V1 DBA recommendation. No ORM, migration, API, or deployed schema is implied. The task-management owning spec must adopt the selected model and amend the canonical conflicts in §6 before physical FKs are drawn. This document uses singular, module-prefixed candidate names under foundation FR-105 (`specs/foundation/000-foundation/spec.md:540`).

## 1. Goal and authority

Bind each task to a sealed dataset version; preserve the exact dataset items, config/schema version, guideline version, sampling seed and assignment identity used by every published run; allow deterministic, round-scoped counts without exposing hidden answers. Dataset-021 delegates task/run tables and their true FKs to this later contract (`specs/dataset/021-dataset-ingestion-and-lineage/spec.md:89,104`). Task creation, run lifecycle and workspace consumer semantics come from 013/014/015; ADR-022 owns state transitions; ADR-037 owns task membership checks (`docs/adr/022-task-state-machine-location.md:80-96`; `docs/adr/037-permission-matrix-authorization.md:12-27`).

**Exclusions:** Annotation submissions, review decisions, IAA results and export persistence need separate owning specifications. This draft does not assign them invented physical FKs. Their later schema must reference a stable run/assignment identity and preserve schema/config version as required by the constitution (`specs/_governance/constitution.md:180-187,198-204`).

## 2. Storage approaches

| Approach | Shape | Assessment |
|---|---|---|
| A — relational run membership (recommended) | Immutable run/snapshot rows plus `task_run_item` and stable assignment rows; a manifest digest/ref mirrors the selected ordered IDs | Real item and assignment FKs, indexed list/count queries, reproducible membership. Costs rows proportional to published items. |
| B — external manifest only | Run holds `selection_manifest_ref`, seed and count; assignments refer to IDs inside artifact | Matches 014's external-list wording but cannot constrain item membership, make efficient run/item joins, or prove the manifest matches published assignments in SQL. |
| C — one JSON task/run document | Task stores rounds, selected items and assignments in JSON | Low table count but weak uniqueness/FK enforcement, expensive updates, and unclear historical identity. Conflicts with normalized core relationships and SQLite portability. |

Select A for the owning spec. `selection_manifest_ref` can remain an audit/export artifact pointer as 014 describes (`specs/task-management/014-task-detail/spec.md:764-765`), but the relational membership is the authoritative fixed item set. Publish validates a digest over an ordered canonical ID list and writes manifest receipt, membership, assignments, run and transition atomically. Do not duplicate answer-bearing source artifacts in this manifest. **Selected V1 lifecycle:** one immutable `task_run_cycle` per trip from draft through trial rounds toward Official Run; a return to draft closes that cycle, and the next Dry Run opens a new numbered cycle whose rounds start at R1. A task has at most one lifetime Official Run because ADR-022 has no return from `official_run_in_progress` or `completed` to draft (`docs/adr/022-task-state-machine-location.md:85-96`). Historical cycles never disappear.

**Current task columns versus historical versions.** `task.current_run_cycle_id`, `task.status`, current config/guideline pointers and `trial_round` display are mutable current-state projections. A current run/snapshot is derived within `current_run_cycle_id`, not held by a second task-level pointer. Current config/guideline pointers can be nullable only during initial task/version creation inside a transaction, then set before commit; use a service check to reject any committed task missing them until a safe DB `NOT NULL` sequencing is available. A past `task_run` and its snapshot never resolve provenance by following these pointers; use its locked cycle, snapshot and round FK. `task_type` in the 014 `TaskDetail` aggregate is derived from composable `outputs[]` for legacy display/export, not a normalized task-type discriminator (`014:757-758`; `013:859`; ADR-029:37-46).

**Review roster:** `reviewer_ids` and `arbiter_ids` are projections from `task_reviewer_roster_member`, with `can_arbitrate=true` expressing the subset (`014:645-648,757`). This selects normalized rows over validated config JSON: task/member uniqueness and a `(task_id,sort_order)` index serve roster editing, effective-pool checks and deterministic assignment without repeated JSON scans. At publish, copy the active selected candidates and their stable order into `task_run_reviewer_candidate` in the same transaction; this costs O(reviewers × runs) small history rows but preserves the exact historical input without duplicating **current** roster state or treating it as a sticky review assignment. The later review owner continues to derive actual reviewer stickiness from submissions per 015 FR-093(5). If membership is later disabled, the snapshot stays intact for audit but grants no live authority.

## 4. Integrity, transactions and query costs

1. **Creation:** Save a validated config and guideline version, task bound to a sealed `dataset_version`, and the creator's `project_leader` membership in one transaction. Idempotency key semantics come from 013 FR-006d (`013:617-620`); key storage shape belongs to the API/idempotency contract, not this table list. No cycle, run item or assignment is created at task creation (`014:612`).
2. **Dry publish:** Within one transaction verify current task state, sealed dataset, validated config and public/protected field mapping, active membership counts, complete prior round, revision notes, and latest IAA status per ADR-022/014. Lock task/current version rows (PG `SELECT FOR UPDATE`; SQLite `BEGIN IMMEDIATE` or equivalent serialized write). For R1, open the next numbered cycle and pin dataset/config/seed/algorithm; for Rn in the same cycle, reuse the pinned pool. Select public item IDs deterministically, exclude items already used by earlier dry rounds in **that cycle**, create round, per-run snapshot, run, run items, assignment slots and transition. Commit together or none. A uniqueness violation on a concurrent publish must yield the existing publication for a matching idempotency key or a conflict; never silently create a second run.
3. **Official publish:** Derive remaining items from that cycle's sealed dataset version minus its published trial run membership; reject zero (`014:614,723`). In the same locked publication transaction, select the task's current guideline version and pin its same-task FK on the new Official run; this may differ from the latest Dry round after a waiting-stage guideline edit. Lock the exact remaining IDs in a new Official snapshot/run, then make exactly one assignment slot per item and allocate in stable member order; `min_annotators` does not multiply official slots (`014:615`). Verify `item_count` against actual run item rows before commit. No second Official Run is created in the **task lifetime** under ADR-022's current state machine; retry returns the prior publication.
4. **Draft reset / reassignment / exclusion:** `waiting_iaa_confirmation → draft` closes the current cycle as rejected, clears only current pointers, and preserves its rounds, snapshots and assignments. A later Dry publish starts cycle `N+1` at R1, even if it reuses an item from the rejected cycle. Preserve assignment slot `id`; set pending slot's assignee to null when the selected annotator membership is deactivated, leave submitted history intact, then reassign or exclude (`014:588-590,594`). A null assignee does not indicate exclusion; the exclusion row does. V1 exclusion is terminal and never deleted/reversed; an erroneous exclusion requires a later explicit corrective product workflow, not mutation of history. Compute submitted denominators from nonexcluded assignment slots in `task_id × cycle × run_type × round` scope (`014:653`).
5. **FK and index budget:** Index every child FK not already leading a PK/unique index: task creator/version/current pointers; config/guideline/cycle task IDs; cycle dataset/config; round cycle/guideline; snapshot cycle; run cycle/snapshot/round; run item item ID; roster/pool membership; assignment task/run/item/membership; exclusion actor; transition actor. Add `(user_id,membership_status,task_id)` for my-tasks lookup, `(task_id,cycle_no)` already unique for cycle history, `(task_run_cycle_id,run_type,created_at)` for run history, `(task_run_id,assignee_membership_id)` for workload, and `(task_id,triggered_at,id)` for audit pagination. Keep PK/unique btrees as the leading run-item/run-assignment lookup indexes. Do not add JSON GIN indexes without a demonstrated key predicate/EXPLAIN cost; config is primarily read by version ID (`backend-constitution:69,125`; `.claude/agents/senior-dba.md`, Database Standards).
6. **3NF and scoped FK exception:** Task identity, config content, guideline content, cycle/version facts, round facts, item membership and assignment slots depend on separate keys. Derived counts, review status, `task_type`, dataset ancestry and current reviewer load do not become duplicated stored facts. The config row holds both the complete immutable schema/config and its schema version marker; snapshot references that row rather than duplicating its JSON. The run pins a guideline FK because Official has no trial-round FK; Dry run guideline equality to its round is enforced by a composite FK, so this temporal reference cannot diverge. `task_id` is intentionally repeated in round, run and assignment **only** to support database-enforced same-task composite FKs; those FK constraints force its value to equal the parent task. Same-cycle run→round/snapshot is likewise DB-enforced. Dataset item→version membership, `dataset_version.state='sealed'`, current active annotator role, legal state transition, full set counts and algorithmic assignment remain service-transaction checks: ordinary FKs/CHECKs cannot express them without prohibited dataset ancestry duplication or cross-row predicates. The manifest stores an integrity digest/ref, not a second mutable source of assignment truth.

## 5. SQLite and PostgreSQL mapping

| Concern | PostgreSQL 16 | SQLite Lite | Required shared rule |
|---|---|---|---|
| UUID | `uuid` | canonical lowercase UUID text | Validate format at Pydantic boundary; nonnull PK and FK on both. |
| Variable config/overrides | `jsonb` | SQLAlchemy `JSON` stored as text (`JSON().with_variant(JSONB(),'postgresql')`) | Validate typed payload before write; use dialect-neutral access (`docs/adr/024-database-quickstart-sqlite-tiered.md:85-95`). |
| UTC time | `timestamptz` | ISO-8601 UTC text or SQLAlchemy UTC-normalized datetime | UTC normalization and ordering tested on both; avoid local timestamps. |
| Boolean/enum | `boolean`, CHECK/text enum | integer affinity, CHECK `IN (0,1)`; text CHECK | Use explicit CHECK for run type/status and positive values; do not assume SQLite type affinity enforces a domain. |
| FK | enforced normally | `PRAGMA foreign_keys=ON` on every connection | Explicit child indexes, same-task composite FKs where possible. |
| Nullable unique | multiple NULLs permitted | multiple NULLs permitted | A `(task_id,run_type,trial_round_id)` unique does **not** make official run unique. Use separate partial unique indexes, or a nonnull execution/run key after owner decision. |
| Publish concurrency | row lock/serializable retry or atomic insert conflict handling | single writer / `BEGIN IMMEDIATE` and busy retry | Compare expected state/version and create run/items/assignments/transition atomically. SQLite Lite is not multiuser production (`ADR-024:29-46,85-95`). |

**Selected natural uniqueness:** enforce `UNIQUE(task_run_cycle_id,round_no)` on rounds, unique Dry `trial_round_id` (nonnull only for Dry), and unique Official **task ID** `WHERE run_type='official_run'`. Both engines support partial unique indexes; test their predicate equivalence. The cycle table's open-row partial unique index prevents two concurrently open cycles for one task. `UNIQUE(sample_snapshot_id)` and task-scoped publication idempotency key uniqueness apply separately. Do not use `(task_id,run_type,trial_round_id)` with a nullable round as an Official uniqueness guard.

## 7. Security and verification expectations for later phases

Task/run queries read `dataset_item.public_payload` through the run-item FK and build allowlisted response models; they never join `dataset_item_private` or read restricted `source_ref`. Creator preview of raw files is restricted to the pre-ingestion local flow. Post-ingestion stored answers are scoring-worker only (`dataset-021:99-103`; `specs/_governance/testing-constitution.md:90-95`). The `field_role_map` must be validated against **every bound batch's** public/protected classification before publish; an explicit Output preannotation in 013/015 is permitted only when public (`013:584`; `015:987`; `dataset-021:97,100`). PostgreSQL query roles must have no private-table read grant; SQLite enforces the equivalent repository/service boundary and public allowlist (`dataset-021:101,103`).

Authorization still requires current active task membership, relevant permission-matrix cell, and assignment/role/resource check. A matrix allow cannot reveal a hidden task or hidden answer; query parameters are not authority (`ADR-037:12-27`). Keep peer annotations isolated until task config explicitly allows consensus visibility (`constitution:191-193`).

At implementation time, use separate Red tasks for FK/unique/round isolation, concurrent duplicate publish, member deactivation/reassignment, idempotency, SQLite and PostgreSQL transactions, and recursive answer leakage; migration upgrade/downgrade/roundtrip are distinct tasks and migration PR stands alone (`testing-constitution:13-17,41,90-95`; `backend-constitution:55-69`). The later performance gate should inspect EXPLAIN plans for run list, member queue and task history before adding JSON GIN indexes. This draft performs no such tests and makes no deployed-schema claim.
