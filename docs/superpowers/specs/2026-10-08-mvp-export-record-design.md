# MVP 匯出紀錄與原始產物設計（issue #1160）

## 目的與範圍

讓任務結果匯出可依原始檔案重新下載，並追溯每一個納入的執行、版本與抽樣快照。這是資料庫**規劃契約**；本切片只修訂 014 正典、候選欄位字典、盤點總帳與 NoteCraft 資料，不建立 ORM、migration、API 或物件儲存服務。使用者已要求表與圖的說明採繁體中文，英文僅作技術識別碼。

成功條件：同一匯出紀錄重新下載時回傳原始 bytes 與原檔名，標記或審核後續異動不改變檔案；跨多個 run 的每列結果均能追溯其固定版本；過期、撤銷、損壞或失權時不提供檔案；標記者不可由匯出或歷史紀錄取得私有答案或未提交審核草稿。規格來源為 014 FR-009a、FR-010i-1／2、FR-015e／g／h、FR-020／021／024、主憲法 XVI／資料保留條款與 ADR-024／037。

## 決策

1. 首次匯出只走一條內容產生與驗證路徑，原子保存不可變原始檔案，再把歷史列設為可下載。條件快照是審計與重製依據，不是重新下載時查詢當前標記的指令。重新下載重新驗證 `dataset.export`、當前 task 範圍、產物狀態、期限與 SHA-256，讀取同一原始檔案；不新增歷史列、不讀畫面篩選或當前切詞引擎。新建詞級匯出時仍需有效切詞引擎與版本。
2. `task_export` 一列代表一次匯出請求及一份原始產物，含 UUID 主鍵、task／請求人 FK、格式及格式版本、已驗證的條件快照、狀態、原檔名、受限物件參照、SHA-256、位元組數、完成與到期時間、撤銷時間。`scope_label`／`export_type` 是顯示欄位，不混入重建條件。狀態只記 `pending → processing → ready | failed`；到期與撤銷由各自時間欄判定，不製造重複狀態。
3. `task_export_run` 一列代表一個匯出納入的一次執行，複合 PK `(export_id,run_id)`，正整數 `position` 保持輸出順序；`task_id` 是為兩端同任務複合 FK 所需的受控冗餘。`(export_id,position)` 唯一。條件快照另存有序 `selected_runs[]`，每項有執行身分、階段及固定版本／快照；共用篩選條件放在全域 `filters`，混合階段時頂層 `run_stage` 必須為 `all`。每個 run 的 dataset/config/schema/guideline/snapshot 身分沿不可變 run／cycle 鏈解析並寫入產物 `manifest.runs[]`，不在此關聯表重複存版本欄。
4. 格式版本明列於檔案與歷史列。`json` 維持 `{manifest,items[]}`；`json-min` v2 改為 `{manifest,rows[]}`，使零列檔案也含版本與請求人 metadata。這是格式破壞性變更，014 需升 MAJOR 版本並保留舊版歷史檔案的原始 bytes；不靠新版序列化器改寫舊檔。
5. 原始產物保留 30 日，匯出歷史 metadata 保留一年；刪除來源或權限撤銷時立即停止下載。歷史列過期後可顯示「已過期」，不延長舊產物期限。冪等鍵以任務、原請求人及客戶端鍵為唯一範圍；摘要涵蓋經規範化的任務／請求人、格式與版本、有序執行、篩選、語言和序列／切詞選項，不含伺服器產生的時間或產物資料。先授權再查重，worker 依匯出 ID 重試，避免跨請求人誤取歷史列。僅內部受限物件位置入庫，任何公開 API 均不回傳原始儲存路徑。

## 設計邊界與驗證

兩張表皆為未部署候選。UUID、JSON／JSONB 與 UTC 時間分別依 ADR-024 適配 SQLite Lite 與 PostgreSQL；複合 FK 父端先有同序 UNIQUE。索引先用 `task_export(task_id,requested_at DESC,id DESC)`、`task_export_run(run_id,export_id)` 及兩個唯一鍵，JSON 條件不預設 GIN。實作階段須用兩種資料庫檢查 FK、唯一性、重試、到期、撤銷、損壞、內容完整性及答案隔離；本文件的 NoteCraft 線只畫已確認的單欄 FK。

014 FR-021 現行「每次以快照重建」與不可變原始產物相衝突，FR-010i-1 單一 run metadata 又無法描述跨 run 匯出；因此先以 OpenSpec 修正正典與驗收，再投影字典與圖。原型目前可能仍模擬舊下載流程，正式實作必須另走 Red／Green 和 API／migration 分拆，不以此規劃 PR 宣稱行為已落地。
